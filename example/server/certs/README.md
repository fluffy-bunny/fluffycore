# Checked-in dev mTLS bundle

**Throwaway development/test fixtures. Not secrets, not production
credentials, safe to be public.** Regenerated by `gencert` (see
`middleware/auth/mtls/README.md`), never hand-edited.

| File | What it is |
| --- | --- |
| `ca.pem` | Self-signed dev CA certificate |
| `ca-key.pem` | Dev CA private key -- only needed to issue *more* leaf certs with this same CA; the server never reads it |
| `server-cert.pem` / `server-key.pem` | Server certificate (CN=`localhost`, SAN=`localhost`,`127.0.0.1`), signed by the dev CA |
| `client-cert.pem` / `client-key.pem` | Client certificate (CN=`fluffycore-dev-client`), signed by the dev CA |

All four certificates are valid for ~100 years (`gencert --forever`) so this
bundle never needs to be regenerated just because it expired.

## Why these are checked in

`example/internal/contracts/config`'s default config points
`tlsCertsDir` at this directory, so cloning the repo and running (from
`example/server`, since it reads `config/clients.json` relative to its own
directory) `APPLICATION_ENVIRONMENT=Development go run . serve` brings the
server up with mutual TLS **on by default**, no setup step required -- see
`middleware/auth/mtls/README.md` for how to dial it and how per-method mTLS
enforcement works.

## Why the private keys being committed is fine here

Every key in this directory was generated solely for this purpose and has
never protected anything real. Committing a private key is normally a hard
no -- these are the one deliberate exception, made safe by three things
holding at once:

1. **The CA only ever signs fixtures for this repo.** It has no relationship
   to any production identity, service, or environment.
2. **A real deployment overrides every one of these paths.** `tlsCertFile`
   / `tlsKeyFile` / `tlsClientCAFile` (or `tlsCertsDir` itself) pointed at a
   real issuer -- HashiCorp Vault's PKI secrets engine via Vault Agent or the
   Vault Secrets Operator/CSI provider, in this project's case -- always wins
   over this directory; see `contracts/config.CoreConfig`'s doc comments.
3. **If it were ever exposed, the blast radius is "someone can complete a
   TLS handshake against a local dev instance of the example app."** No
   cluster, tenant, or customer data is reachable through it.

If your secret-scanning tooling (GitHub push protection, GitGuardian, ...)
flags the `EC PRIVATE KEY` blocks here, that's the scanner doing its job
correctly on a generic pattern match -- allowlist this path rather than
disabling the scan.

## Regenerating

From the repo root:

```sh
go run ./cmd/cli gencert --out ./example/server/certs --forever --force \
  --host localhost --host 127.0.0.1 --client-cn fluffycore-dev-client
```

Only do this if the bundle needs to change shape (new SANs, a new client
identity, ...) -- there's no expiry-driven reason to.
