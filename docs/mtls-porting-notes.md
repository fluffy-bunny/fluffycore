# Porting mTLS Support to a Different gRPC Framework

`middleware/auth/mtls/README.md` documents fluffycore's mTLS feature well, but it's written for readers already fluent in fluffycore's own conventions — `contracts/common.IEntryPointConfig`, `middleware/claimsprincipal`'s claims-AST, `dicontext`'s request-scoped DI container, `cobracore`/`cmd/cli`, `example/server`. None of that exists in another codebase. If you're porting this feature elsewhere, read this page first: it separates what genuinely ports (stdlib `crypto/tls` + `google.golang.org/grpc` mechanics) from what's fluffycore-specific glue, and lists the mistakes made — and fixed — while building this, so they don't get rediscovered the hard way in the new codebase.

---

## Copy near-verbatim

These have zero fluffycore coupling beyond a plain config struct, and can be lifted essentially as-is:

- **[`utils/certgen`](../utils/certgen)** (`certgen.go`, `bundle.go`) — self-signed CA + leaf certificate generation (ECDSA P-256), a `Bundle`/`BundleOptions` convenience layer, and the `--forever` (100-year) validity convention for a checked-in dev bundle. No framework imports at all.
- **[`runtime/servertls/servertls.go`](../runtime/servertls/servertls.go)** — builds a hot-reloading `*tls.Config` via `GetCertificate`/`GetConfigForClient` callbacks that re-stat and reload the cert/key/CA bundle from disk whenever they change. The only fluffycore dependency is `contracts/config.CoreConfig` as the input parameter type, which is a plain struct — trivial to swap for whatever config type the target framework uses.
- **The detection logic in [`middleware/auth/mtls/mtls.go`](../middleware/auth/mtls/mtls.go)**: `peer.FromContext(ctx)` → type-assert `credentials.TLSInfo` → check `tlsInfo.State.VerifiedChains` → pull CommonName/fingerprint/URI SANs off the leaf certificate. This is pure `google.golang.org/grpc` plus stdlib. Only *what happens with the result* is fluffycore-specific (see below).

## Needs re-targeting, not copying

- **Where the resolved identity gets attached.** fluffycore adds claims (`mtls_verified`, `mtls_cn`, `mtls_fingerprint`, `mtls_san_uri`) to a DI-scoped `IClaimsPrincipal`. The *what* (these four facts about the connection) ports directly; the *where it goes* needs to become whatever the target framework uses to carry per-request identity/authorization state.
- **Per-method enforcement.** fluffycore uses `IEntryPointConfig` plus a claims-AST `Or`/`And` gate keyed by full gRPC method name. The concept ports (TLS stays connection-wide and optional; a claim decides per-method whether to require it) but the mechanism is fluffycore's own authorization engine — reimplement against whatever the target framework already uses for per-method authorization.
- **CLI cert-generation wiring** (`cobracore/cmd/gencert`, `cmd/cli/root/gencert`) — this is cobra-specific plumbing around `certgen.NewBundle`/`.WriteFiles`. The wrapped logic is portable; the cobra command boilerplate needs to become whatever CLI framework (if any) the target project uses.

## Not applicable elsewhere

`example/server`'s directory structure, `contracts/config.CoreConfig`'s specific field names, `wellknown/claim-types.go`'s claim-type constants, and `example/server/certs/README.md`'s "why committing dev private keys here is fine" framing (the argument itself still holds in a new repo — CA/cert generated solely for that repo's own fixtures, never protecting anything real, always overridden by real deployment config — just re-state it there rather than copying the file).

## Gotchas hit while building this

1. **CA-validity overflow.** A "CA valid = leaf validity × 5" scheme overflows `time.Duration`'s int64 nanosecond range once leaf validity passes roughly 58 years — exactly what a 100-year (`--forever`) leaf triggers. The overflow silently fell back to a hardcoded 5-year default CA validity, producing a CA that expired *before* the certificates it had signed. Fix: detect the overflow (multiply, then divide back and compare) and fall back to CA validity equal to the leaf's validity — never shorter, just not padded 5x. See `caValidForFrom` in [`utils/certgen/bundle.go`](../utils/certgen/bundle.go).
2. **`VerifiedChains` vs. `PeerCertificates`.** `credentials.TLSInfo.State.PeerCertificates` can be populated even when the certificate was never cryptographically verified (Go's `tls.RequestClientCert` mode requests a cert but never verifies it). Always gate claim population on `VerifiedChains` being non-empty; gating on `PeerCertificates` alone would trust an unverified or self-signed certificate.
3. **A gRPC-gateway's internal client connection dialed with hardcoded insecure credentials breaks once the backend requires TLS.** fluffycore's `runtime/runtime.go` dials its own just-started gRPC server with `grpc.WithTransportCredentials(insecure.NewCredentials())` to power the REST gateway; enabling TLS on that gRPC server breaks that internal hop (`error reading server preface: EOF` or a reset connection). This turned out to be pre-existing and unrelated to the mTLS work in fluffycore's case (it reproduces identically with TLS fully disabled, i.e. the gateway path was already broken) — but any framework with the same "gateway dials its own backend insecurely" pattern needs that internal dial upgraded to TLS once the backend starts requiring it.
4. **viper's env-var naming for camelCase config keys.** A config key like `tlsCertsDir` becomes the env var override `EXAMPLE_TLSCERTSDIR` (uppercased as one word, no inserted underscore) under viper's `AutomaticEnv`, not `EXAMPLE_TLS_CERTS_DIR`. Verify this empirically for whatever config library the target framework uses rather than assuming underscore-insertion.
5. **Verify AND/OR claim composition with a real test, not by inspection.** fluffycore's claims AST requires wrapping two alternatives in a single `Or`-entry's own `And` list to get true OR semantics — putting them as two siblings directly in an `Or` slice ANDs them together instead, since a node's peers are always combined by *that node's own* operand, not automatically OR'd just because they sit in an `Or` slice. This is specific to fluffycore's AST implementation, but the general lesson travels: whatever authorization-composition mechanism the target framework uses, write a test that exercises the actual boolean logic before trusting a hand-built expression — this exact mistake shipped once here and was only caught by testing, not by re-reading the code.
